# 관계자 인터뷰 → 검증 가능한 요구사항 명세

## 먼저 해야 할 일

사용자가 '최대한 효율적으로'라고 말했을 때 최적화 목적을 임의로 지정하지 않는다. **누구를 위해, 무엇을, 어느 조건 아래에서, 어떻게 평가하는지**를 식별한다.

## 질문의 우선순위

| 단계 | 얻어야 할 정보 | 질문 예시 |
| --- | --- | --- |
| 목표 | 결정의 성공·실패 정의 | '이번에 최종 결정할 항목은 무엇인가요?' |
| 강제 제약 | 절대 위반할 수 없는 조건 | '반드시 지켜야 하는 시간·수량·안전 조건이 있나요?' |
| 선택 제약 | 선호·페널티로 표현할 내용 | '가능하면 만족시키되 예외가 허용되는 조건인가요?' |
| 데이터 | 단위·기간·키·품질 | '근거가 되는 표와 업데이트 시점은 무엇인가요?' |
| 충돌 | 이해관계자마다 다른 규칙 | 'A가 말한 규칙과 B가 말한 예외는 언제 적용되나요?' |
| 평가 | 검증 가능한 합격 조건 | '실제 결과가 성공했는지 무엇으로 확인하나요?' |

### 높은 가치의 질문을 고르는 법

- 답에 따라 모델이 크게 달라지는 **목표/제약/예외**부터 질문한다.
- 이미 증거가 있는 사실은 반복해서 묻지 않는다.
- 독립적인 질문을 묶을 수 있지만 '예/아니요' 여러 개를 하나의 질문에 섞어 대답을 왜곡하지 않는다.
- 질문 횟수·답변 속도에 제한이 있으면, **질문 후보 생성과 증거 정리**를 분리해 중복을 줄인다.
- 답변이 명확하지 않으면 '미확인'으로 남긴다. 임의의 수치를 채우지 않는다.

## 증거 장부(evidence ledger)

| ID | 주장/조건 | 출처 | 확인 시점 | 상태 | 모델 영향 |
| --- | --- | --- | --- | --- | --- |
| E01 | 가상 차량 좌석 수 40석 | 제공된 예시 데이터 | 예제 작성일 | 확정(예시 내) | 강제 제약 |
| E02 | 일부 정류장 조기 도착 요청 | 가상 관계자 발언 | 예제 작성일 | 확인 필요 | 선호/강제 구분 필요 |
| E03 | 노선 이동시간 | 입력 없음 | - | 미확인 | 실제 계산 보류 |

위 표의 인물·조건은 합성 예시이며 실제 회사·대회 자료가 아니다.

**상태 분류:** confirmed / tentative / conflicting / unknown. 확정 상태는 특정 문제의 '제공된 사실'이라는 의미이며, 외부 세계의 보편적 사실을 의미하지 않는다.

## 인터뷰 결과를 모델로 넘기는 계약

- 결정권자와 결과물 사용자
- 필수 목표 및 우선순위
- 강제 제약, 예외조건, 선택적 선호
- 단위·기준일·집계 단위가 붙은 입력 데이터
- 근거와 규칙의 충돌 목록
- 미확인 질문과 모델링 가정
- 테스트 가능한 수용 기준

## 실패 사례

- '가능하면'을 무조건 지켜야 하는 제약으로 변환해 불가능한 모델 생성.
- 이해관계자 A의 의견을 전체 조직의 정책으로 단정.
- 데이터에는 날짜가 없는데 미래 일정의 정확성을 보장.
- 출처가 없는 기준·가격·품질 임계값을 만들어 최적화를 수행.
- 모르는 요구조건을 추론해 채워놓고 인터뷰 완료로 간주.
